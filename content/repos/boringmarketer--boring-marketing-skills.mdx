## 它是什么

Boring Marketing Skills 是 32 个面向 AI Agent 的免费营销 Skill，作者 James Dickerson，MIT 许可。README 说它们是为 Claude Code、Codex、Cursor 等编码代理准备的，按客户认识商家的顺序分组，每个 Skill 都不依赖付费工具。它解决的不是「让 Agent 写一句文案」，而是「营销流程很长，Agent 每次都要从头理解业务」：先用一个入口 Skill 把品牌上下文写成文件，后续 Skill 复用这些文件，按客户旅程的阶段逐步执行。

给谁用？README 的定位很明确：做本地商家营销的人、代理商和自由职业者，以及想给自己的业务做营销的独立开发者。技能覆盖调研、定位、文案、落地页、SEO、AI 搜索、广告、邮件和内容，另有一套面向本地商家的深包。

核心组成可以按 README 的分组理解。`start-here` 负责读业务、写品牌文件并告诉你下一步；随后是「被找到」「被选中」「被联系」「被召回」「赢客户」和「自我营销」几组。每个 Skill 是一个独立文件夹，可以给每个客户单独建一套。

和泛泛的提示词包相比，README 强调的差别有三个：按客户旅程排序、共享品牌上下文，以及每条工具建议都先给免费路径。README 称这些 Skill 来自真实投放项目，但这是项目自述，没有第三方复现。

## 它替掉了什么麻烦

它替掉的是「每换一个营销环节，就要向 Agent 重讲一遍业务，还要自己记住先做什么后做什么」这套手工接力。README 没有交代出现之前的标准做法；编辑判断：过去要么把调研、定位、文案、投放拆给不同人或不同对话，业务背景在每次交接里损耗；要么用一份大提示词一次性生成全部内容，步骤之间没有输入输出边界，出了问题也说不清是哪一步错了。

它的切入点是把营销拆成有顺序的阶段。README 说这些 Skill 按「客户认识商家的顺序」分组，`start-here` 读业务并写品牌文件，其余 Skill 读取同一份上下文。编辑判断：这把「一次生成」换成「分步执行 + 共享上下文」，好处是每一步的输入和产出相对明确，代价是入口那一步写偏，后面全部跟着偏。

和同类方案的差别，README 没有列举竞品，也没有做功能对比，只说明所有 Skill 都不需要付费工具，并且每条推荐先写免费做法。编辑判断：与「提示词合集」相比，可确认的差异是路由（告诉你下一个跑哪个）、项目级品牌文件（避免重复解释业务）和可验证的检查（例如用暂停测试对照电话记录）。README 未说明它的效果与人工营销或付费 SaaS 的量化差距。

## 跑起来要几步

两步：装好 Skill，然后用 `/start-here` 启动。任意 Agent 用：

```bash
npx skills add boringmarketer/boring-marketing-skills
```

Claude Code 插件方式：

```
/plugin marketplace add boringmarketer/boring-marketing-skills
/plugin install boring-marketing@boring-marketing-skills
```

装好后输入 `/start-here` 并说出业务名。README 说它会读网站和评论、写出其他 Skill 共用的品牌文件，然后告诉你下一个该跑哪个 Skill，首次大约 3 分钟。给客户做的话，对 `/start-here` 说 “new client”，它会建独立文件夹。

预期结果是拿到一套品牌文件和一个下一步建议，而不是一次性生成所有营销文案。常见卡点：部分 Skill 需要 Agent 有联网能力去读网站和评论；广告、Meta API、Google Ads API、关键词数据等环节在 README 的推荐栈里对应第三方服务，README 说每个 Skill 都给了不付费的做法，但需要 key 的部分要按 `TOOLS.md` 配置。README 没有给出统一的安装前置版本要求，也没有说明 `/start-here` 会写入哪些文件、如何回滚。

## 它把复杂度放在哪

复杂度放在「按阶段路由 + 共享品牌文件 + 把检查写进 Skill」这三层。README 说分组是有顺序的：先建立品牌上下文，再解决「被找到」，然后才是「被选中」和「被联系」。这种路由比让 Agent 一次生成全部内容更可控，因为每一步的输入和产出都相对明确。

共享品牌文件是第二个关键抽象。`start-here` 写的文件被其他 Skill 读取，避免每个 Skill 重新问一遍业务是什么。代价是入口这一步的质量会影响后面所有环节；如果品牌文件写偏了，后续产出会跟着偏。编辑判断：这类项目级上下文很适合长期服务同一个客户，但换客户时要明确切换文件夹，否则容易串味。

第三个设计是把「可验证的检查」写进 Skill，而不只是生成文案。README 举例说 `ads-incrementality-check` 用暂停测试对照电话记录，判断广告是真带来线索还是只抢归因；`first-screen-check` 按手机首屏检查号码、承诺和证明。README 用三个真实项目里的发现解释这些 Skill 的由来，但结果属于项目自述。`site-audit` 像 Google 和 AI 爬虫那样爬站，只排最值得修的几个技术问题；`keyword-research` 把免费 autocomplete 数据整理成主题，而不是一张五千行关键词表。

工具选择上也有一套流程。README 说每个 Skill 在自己的步骤先写免费做法，再列作者常用的付费栈，清单包括 Exa、Firecrawl、DataForSEO、ElevenLabs、Meta Ads MCP 等。`boringfunnels` 是作者自己的产品，README 要求提到它的 Skill 在同一行注明，并说明它不替代免费路径、没有任何 Skill 依赖它。编辑判断：这种披露是加分项，但读者仍应把推荐当作带有商业动机的建议。

## 什么时候别用它

它不适合需要企业级品牌治理、多语言统一管理或严格合规审计的团队，也不适合想要「一键跑完整个营销」的人。MIT 许可，README 明确说可以用在自己的业务、客户项目或产品里。营销声明、广告合规、本地商家资质和平台政策仍然要人负责，Skill 不能替代这些审核。

依赖方面，README 说所有 Skill 都不依赖付费工具，但「能跑」不等于「效果一样」：AI 搜索、SEO、广告归因的结论会随平台和地区变化，第三方 API 也需要自己维护 key 和额度。README 未说明这些 Skill 在模型能力较弱时的降级表现，也未说明更新频率。

数据与隐私上，Skill 会读网站、评论和公开信息；如果用于客户项目，评论和业务数据的抓取范围要自己控制。README 未说明数据留存策略，也未给出每个 Skill 的评测或准确率数据，也没有说明第三方服务如何处理抓到的数据。编辑判断：给客户做营销时，先确认抓取范围和客户授权，再让 Agent 读站。

它的设计是分阶段、可检查，而不是全自动，所以期待「输入业务名就产出完整营销方案」的人会失望。编辑判断：它更适合愿意按步骤审阅、能在每一步补上人工判断的运营者；如果团队没人能判断产出好坏，32 个 Skill 只会把错误放大到更多渠道。
