## 它是什么

`/grill-me` 是 `mattpocock/skills` 里的一个用户触发 Skill，作用是在动手之前，让 Agent 围绕你的计划或设计持续追问，直到设计树的每个分支都有答案。README 把它归在 productivity 分类，定位是“非代码场景”的访谈工具。

这个仓库本身是 Matt Pocock 日常使用的 Agent Skills 集合，分 engineering 与 productivity 两类。README 说这些 Skill 故意做小、容易改、可组合，能配任何模型，也不接管整个开发流程。`/grill-me` 只负责发起访谈，真正的访谈纪律放在 `grilling` 这个 model-invoked（模型可自动调用）Skill 里；`grilling` 还被 `grill-with-docs`、`triage`、`wayfinder`、`improve-codebase-architecture` 复用。

三者关系可以这样理解：`grilling` 是可复用的访谈原语；`/grill-me` 是最薄的用户入口；`/grill-with-docs` 是同一场访谈加上文档产出，会同步打磨术语、更新 `GLOSSARY.md` 和 ADR。README 还说用户触发型 Skill 的职责是编排，它可以调用模型触发型 Skill，但不能再调用另一个用户触发型 Skill，所以 `/grill-me` 调用 `grilling` 是允许的。README 还把 `grill-with-docs` 里的共享语言称为可能是这个仓库最酷的技术。

给谁用：任何准备改东西、又担心 Agent 理解偏差的人。README 的原话是每次想做一个改动都该用它们。另需区分：`RobMitt/grill-me-skill` 是另一个独立 Skill；README 未提及它，本文按 `mattpocock/skills` 里的 `/grill-me` 建档，两者不要混为一谈。

## 它替掉了什么麻烦

它替掉的是“Agent 没做我要的东西”这类返工，办法是在写代码前先补上人和 Agent 之间的沟通缺口。README 把“最常见的失败模式”称为 misalignment：你以为对方知道你要什么，等看到成品才发现它根本没理解。到了 AI 时代，你和 Agent 之间同样存在 communication gap。

README 没有描述在此之前大家具体用什么替代流程，只引了《程序员修炼之道》里那句“没人确切知道自己想要什么”，然后把修复方式定为 grilling session：让 Agent 就你要做的东西提出详细问题。它认为对齐要发生在动手之前，而且要真的往深里想这次改动。

这和 GSD、BMAD、Spec-Kit 这类流程方案不是同一路线。README 说它们试图靠“拥有整个流程”来帮忙，代价是拿走你的控制权，并且让流程本身的 bug 很难排查。仓库里的 Skill 反过来：小、可改、可组合，用的是几十年工程经验沉淀的做法，你可以随便改。仓库内也有现成对照：`/to-spec` 明确“No interview, just synthesizes what you've already discussed”，适合讨论已经很充分、只差落成规格的场合。

## 跑起来要几步

跑起来是三步：装一次、每个仓库配置一次、之后用 `/grill-me` 触发访谈。

安装按 Agent 选一种，不要同时装插件和 `skills.sh`，README 说同时装会让每个 Skill 出现两次。Claude Code：

```bash
claude plugin install mattpocock-skills@claude-plugins-official
```

Codex：

```bash
codex plugin marketplace add mattpocock/skills
codex plugin add mattpocock-skills@mattpocock
```

其他 Agent 或想要可编辑文件，用 `skills` CLI：

```bash
npx skills@latest add mattpocock/skills -a <agent>
```

插件会自己更新；`skills.sh` 把可编辑文件拷进项目，需要你手动维护。安装时把 `setup-matt-pocock-skills` 一起选上。然后在每个仓库里运行一次 `/setup-matt-pocock-skills`，它会问你三件事：用哪种 issue tracker（GitHub、GitLab、本地文件或你描述的其他方式）、triage 时打哪些标签、文档存在哪里。

配置完成后，在 Agent 里输入 `/grill-me`，再说明你要做的计划或设计。README 未说明卸载步骤，也没有统一的升级说明；用 `skills` CLI 时可用 `npx skills@latest update` 更新，插件则由客户端自己管。README 把安装这一节叫作 30-second setup，配完 setup 就表示可以开始了。

## 它把复杂度放在哪

复杂度不在安装，而在访谈：Agent 要把你的计划或设计当成一棵 design tree，持续问到你不再有未解决的分支。README 对 `/grill-me` 的完整描述只有一句“Get relentlessly interviewed about a plan or design until every branch of the design tree is resolved”；对 `grilling` 原语，则把对象扩到 plan、decision、idea。

具体到 frontier、rounds 和问题格式，README 未说明。`frontier` 在 README 里只出现一次，位于 `implement-spec` 的描述中，指并发执行实现子 Agent 的 ready frontier，和访谈怎么分批提问没有关系。问答是否分轮、每轮问几个、问题是否带编号和推荐答案，这份 README 都没有交代；要确认只能去读 `skills/productivity/grilling/SKILL.md` 等源文件。

“找事实”和“做决定”的分工同样 README 未说明。它没有讲 Agent 是否该自己查文件、查工具，还是把事实问题也抛给用户；也没有讲访谈中途发现事实缺口该怎么处理。仓库里另有 model-invoked 的 `research` Skill，会针对高可信一手信源调查并把结论写成带引用的 Markdown，但 README 没有把它和 grilling 串起来。

结束条件 README 说得相对明确：每个分支都被解决，才算访谈完成。它没有说明结束后是否自动开工，也没有承诺产出规格、代码或验证结果；README 对 `/grill-me` 的定位始终是访谈。编辑判断：这也是它最容易被误解的地方，访谈完成只代表双方理解对齐，不代表事情已经做完。设计树越往下越宽，问题数量会随分支增长，这是这种做法的固有代价，README 未给出上限。

## 什么时候别用它

只想把已经聊清楚的内容整理成规格，或者团队受不了高强度追问时，别用它。README 把 `/grill-me` 写成 relentlessly interviewed，并建议每次改动都用；编辑判断：这适合需求还模糊、改错代价高的场景，不适合赶时间、只需要归档结论的场景，此时 `/to-spec` 更直接。

许可证：README 未说明。这份抓取文本从开头到 Reference 都没有出现 license 或 MIT 字样，使用前应去仓库根目录确认 LICENSE，不能从本文推断。

模型依赖：README 称这些 Skill 能配任何模型，但没有给出不同模型下的效果对比，也没有说明弱模型是否还能正确推进设计树。访谈成本：README 未说明一次完整 grilling 要多少轮、多少 token、多长时间；relentlessly 本身就意味着它会一直追问，时间和注意力由使用者承担。

会改文件的风险集中在 `/grill-with-docs`：README 说它在访谈中同步更新 `GLOSSARY.md` 和 ADR。编辑判断：如果这些文件在版本控制里，改完必须 review，避免访谈中的临时措辞直接进入长期文档；`/grill-me` 本身不写这些文档，风险小得多。

不适合谁：想要“流程托管”的团队更适合 GSD、BMAD、Spec-Kit 那类方案，代价是 README 所说的控制权；已经想清楚、只差落规格的人适合 `/to-spec`；把 `/grill-me` 当成规格生成器或代码生成器的人也会失望，README 没有给它这些职责。把 `RobMitt/grill-me-skill` 和它混用的人，先分清是哪一个仓库的 Skill。
