## 它是什么

Hallmark 是一个网页设计 Skill，目标写在第一行：拒绝看起来像 AI 生成的页面。它由 Together AI 制作，可装在 Claude Code、Codex、Cursor 和 OpenCode 里，用一句话触发建页、改版或审查。适合能写代码但没有专职设计师的团队，也适合想把 AI 生成页面从模板感里拉出来的个人开发者。

它把设计约束拆成一套可执行的流程，而不是给一段「要好看」的提示词：先立一层永不放行的 Floor，再从 50 套主题里发三套，按访客来页面要完成的事搭结构，最后在真实浏览器里逐项检查机器味特征。README 列出的机器味包括每个标题上方的 eyebrow、字距拉开的全大写标签、标题里一个彩色词、整页空框或只有照片、hero 撑不满屏、每页末尾都塞邮件订阅、表单说「谢谢」却没真的提交。检查完还有一个全新上下文的 reviewer 做终审。

README 还说 v2 段落列了一批更新，包括 50 套主题、按页面任务搭结构、自定义页面、把你的真实产品抓成截图、755 张开放许可照片，以及改版与审查命令。它覆盖的宿主也不只 Claude Code：Codex CLI、Cursor、OpenCode 都能用同一份技能。

## 它替掉了什么麻烦

在它之前，让 AI 做页面常见两条路：一句「做得好看点」的提示词，或直接套模板，前者结果随机、后者每页长得一样。README 未说明这段历史，也没有与其他设计流程的对照实验；这是编辑判断，依据是它列出的机器味清单。README 用 AI slop 指代这类结果，并把「eyebrow」「一个彩色词」这类具体特征当成可检查的靶子，编辑判断：这等于把审美争议翻译成清单。

和同类方案的差别，README 只给了线索而没有逐项比较：Inspired by 段落列出 Impeccable、frontend-design、Kami、taste-skill、UI UX Pro Max、Emil Kowalski 的 skills 和 Vercel 的 Web Interface Guidelines 等项目，说明它站在一组设计 Skill 与指南的肩膀上；具体差异 README 未说明。

## 跑起来要几步

安装一条命令：

```
npx skills add nutlope/hallmark -g
```

`-g` 装到用户目录、所有项目可用，去掉则只装当前项目。README 要求 Node 18 或更高。浏览器检查和截图还需要 `npm i -g puppeteer-core` 以及 Chrome；不装这两个，静态检查仍能跑，只是少了真实渲染这一层。

装好后按宿主调用：Claude Code 落在 `~/.claude/skills/hallmark`，用 `/hallmark <prompt>` 或直接描述要建的页面；Codex CLI 落在 `~/.agents/skills/hallmark`，用 `$hallmark <prompt>`；Cursor 和 OpenCode 会自动找到上面的副本。只想装一个宿主可加 `--agent claude-code`（或 `codex`、`opencode`、`cursor`、`github-copilot`）；也能作为 Claude Code 插件装，先 `/plugin marketplace add nutlope/hallmark`，再 `/plugin install hallmark@hallmark`，调用名变成 `/hallmark:hallmark`。一个常见卡点是 Skill 没有自动触发，README 的建议是点名它：用 `use hallmark to build ...` 开头。

第一次跑的预期流程分四步：读取项目里的字体、配色、框架和锁定的 `design.md`，只问一次素材（照片、截图、真实数字），不自己编；`scripts/theme.mjs deal` 给出三套合适主题，`draw` 按页面任务决定结构；先把 hero 单独做出来并冷审，再铺整页；最后 `scripts/sloplint.mjs --render` 在八个宽度下检查，再由子代理复审。产物是自包含的 HTML 和 CSS，第一行 CSS 注释里记录这次做过的决定。README 未说明无图形环境或无头浏览器的配置方式。

## 它把复杂度放在哪

复杂度集中在三层门槛，这是它和普通设计提示词最大的区别。**Floor** 永不放行，包括对比度、键盘焦点、减少动效、编造事实和手机布局损坏。**Reflex** 是模型容易落入的默认套路，构建时若有理由可以在记录里明确推翻。**Finish** 只是工艺细节，不阻塞发布。分层的好处是「必须对」和「最好有」分开，不会因为一个字号问题卡住整个页面。

主题的定位是另一处设计：一套主题是一种材质，包含纸张、字体、颜色、表面、组件和纹理，并配一张成品页截图；它不规定页面放什么、按什么顺序放。README 说同一主题下两个提示词会得到两张不同的页面，构建时只读一个主题文件，每个文件不超过 8 KB。这意味着主题提供的是视觉语言，结构仍由页面任务决定，避免了套模板的同质化。README 还把结构原则写成一句：预约页负责预约、商店页负责卖货、订阅页负责订阅，动作要落在该品类该在的位置。

改版和审查是另外两条路径。`/hallmark redesign ./src/app` 保留内容和连线、替换设计与布局；`/hallmark audit ./index.html` 只报告不改。`sloplint --before` 会先记录所有链接、字段、事件处理和标题，`--kept` 在改版后如果少了任何一个就判失败，交付时给前后对照。编辑判断：这个「不许丢功能」的检查比视觉规则更有工程价值，能防止 AI 改版时顺手删掉表单或导航。

还有一条 **Custom** 路径：说 custom 就完全不用主题，没有预设结构、组件或配色配方，只保留 Floor、各层 gate 和 `direction.md` 里的一段方向，要求模型找到只有这个客户才有的一个概念来驱动整页。代价是它把决策权交回给模型，README 没有说明这条路径的成功率或验收方式。

## 什么时候别用它

许可证是 MIT，README 的原话是「use it, fork it, ship it」。照片库来自 Wikimedia Commons，只存元数据不存图片，每张照片保留自己的许可证（CC0、公有领域、CC BY 或 CC BY-SA），Hallmark 会在页面上署名；README 明确不用 Unsplash、Pexels、Pixabay，因为这些站点的条款禁止 AI 工具挑选其图片。编辑判断：CC BY 和 CC BY-SA 要求署名，发布前应确认页面上的 credit 没有被删掉，商用前也值得逐张核对许可证。

审美规则是作者的选择，不是普适标准。Floor 里的对比度和焦点有可验证的依据，但「eyebrow 一律不要」「标题不能有一个彩色词」属于风格判断，可能不适合所有品牌。浏览器 lint 依赖 Chrome 和 puppeteer-core，CI 或没有图形环境时需要自己解决，README 未说明无头环境的配置方式。最后那个 fresh-context reviewer 是子代理，不是人类设计师，它能抓一致性问题，但不能替你做品牌决策。

它也不负责内容真实性：README 说素材要由你提供、不编造，但页面上的数字和说法仍要人来核对。编辑判断：它适合已经能写页面、缺的是设计纪律的团队；不适合需要严格品牌规范、或不能安装 Chrome 的构建环境。README 未说明它与设计系统 token、组件库的兼容范围。
