## 它是什么

`skill-distill` 是一个 Skill，回答一个问题：前沿模型把某个任务做对了，换成开源权重模型，给它正确的指令，能不能也做对？它给 Claude Code 或 Codex 用，扮演「老师」；你在一次高质量会话结束时调用它，并指定「学生」——一个 Agent harness 加一个模型，例如 omp 配 DeepSeek-V4.1-Flash。

它面向愿意做评测、并且已经在同时使用闭源与开源模型的团队；不适合只想把提示词缩短一点的人。产出有两样：仓库里可复用的「操作 Skill」，以及针对某一任务、某一模型、某一 harness 的「产物 Skill」。和普通的提示词压缩或经验总结相比，它的差别在于闭环：学生要在干净环境里真的跑，结果要和参考对比，改到对齐为止，最后还要人验收。

## 它替掉了什么麻烦

它替掉的是「把会话经验手抄成提示词，然后希望换个模型也能用」的做法。README 未说明此前团队具体怎么迁移经验；它只把目标写成一句问句，并规定老师要真的启动学生、对比产物、改 Skill、再跑。

编辑判断：手抄式 prompt 的痛点有三处——不知道哪些步骤是必需的，也不知道学生错在哪一步，更无法判断一次成功是不是运气。`skill-distill` 把这三件事拆成可检查的流程：原始 prompt 逐字复用，起始状态清空，每版跑三次，先找第一个出错点再改，最后并排展示参考与学生最佳结果。

和同类方案的差别，README 只给出方法层面的定义；它未点名其他蒸馏工具，也未给出效果对比。编辑判断：它更像「评测协议加记账脚本」，而不是自动压缩提示词的产品。

## 跑起来要几步

四步：装依赖、软链 Skill、发起一次蒸馏、人工验收。前置条件是 `tmux`、`git`、Python 3.10+，以及已安装并指向模型的学生 harness。要为网页类任务截图，还要装 Playwright 和 Pillow：

```bash
pip install playwright pillow && playwright install chromium
```

安装是把 Skill 软链到 Agent 的技能目录：

```bash
git clone https://github.com/sybil-solutions/skill-distill
ln -s "$PWD/skill-distill/skills/skill-distill" ~/.claude/skills/skill-distill    # Claude Code
ln -s "$PWD/skill-distill/skills/skill-distill" ~/.agents/skills/skill-distill    # Codex
```

然后在一次成功的会话末尾说：

> distill this session into a skill for omp with deepseek-v4.1-flash on my local server

老师会按 `skills/skill-distill/SKILL.md` 的循环执行：读会话、写 Skill、在 tmux 里用干净起始状态和原始 prompt 启动学生、对比产物、找到学生第一个出错点并就地改 Skill、再跑；每版跑三次，直到学生与参考对齐。你可以用 `tmux attach -t distill-<task>` 看学生干活。

第一次的预期结果是：得到一个 `student-skill` 形态的产物 Skill、一个 ledger 和 report，以及并排展示的参考与学生最佳结果；只有你执行 `accept`，这次蒸馏才算完成。仓库的 `examples/` 里有完整跑完的样例。

常见卡点：Codex 当学生时要在 `STUDENT_ARGS` 里指定 provider；Claude Code 当学生跑开源模型时要用 `ANTHROPIC_BASE_URL` 指向 Anthropic 兼容服务；opencode 的 JSON 日志在 `extract_session.py` 里还没有解析器。README 没有提 Windows 支持，而 `tmux` 通常意味着 Unix 环境，Windows 用户需要自备兼容层，这一点 README 未说明。README 也没有给出安装耗时或磁盘占用。

## 它把复杂度放在哪

复杂度放在「把变量压到只剩 Skill」这件事上。学生拿到的是与参考逐字相同的原始 prompt、干净起始状态和 Skill，别的都不给；只要 harness 允许，学生自己的全局上下文文件和技能会被关掉。这样对比才能说明「Skill 有没有教会它」，而不是「学生原本就知道」。代价是准备干净起始状态和参考结果本身需要工程，任务越复杂成本越高。参考结果必须先固定下来；README 没有说明参考结果如何采集和存储。

Skill 本身被限制不能作弊：不能包含参考的最终产物，也不能包含一个直接写出产物的脚本；它要教的是步骤、判断、坑和检查，只有在学生无论如何做不对某一小段时才允许放短代码。这条规则把「蒸馏」与「复制答案」区分开。

评估纪律体现在两个数字上：每版三次试验，避免一次侥幸；检查项先在参考上验证，检查在参考上失败就说明检查本身坏了。修正方式是「找到第一个出错点，在那里改 Skill」，而不是整篇重写，这让每次改动可归因。

配套脚本分担记账：`distill.py` 提供 `init`、`trial`、`status`、`wait`、`evidence`、`verdict`、`ledger`、`report`、`accept`；`extract_session.py` 把 Claude Code、Codex、omp 的日志整理成可读参考（会丢掉系统提示和 `AGENTS.md` 文本）；`capture_web.py` 起服务、用无头 Chromium 操作并截图。`templates/student-skill/` 给出产物 Skill 的起始形状；`examples/` 里有跑完的 prompt、产物 Skill、ledger 和截图，可以先对照理解一次成功蒸馏长什么样。

## 什么时候别用它

只想让提示词更短、或不愿承担多轮评测成本的人，不适合用它。许可证是 MIT。适配器成熟度差异很大：README 说 omp 已测试；Codex 作为老师已测试，作为学生需要在 `STUDENT_ARGS` 提供 provider；Claude Code 适配器已写，开源模型要配 `ANTHROPIC_BASE_URL`；pi 已写未测；opencode 已写未测，且日志解析器缺失。换学生之前先确认链路通不通。

成本不只是钱：每版三次试验、多次迭代，再加上老师模型读写会话和对比结果，跑一轮的开销可能远超一次普通会话。原始会话日志保存在 `runs/`，README 说它被 git 忽略，并明确日志含本机路径和上下文；即便如此，日志仍可能包含业务代码或凭据，保留和清理策略要自己定，这是编辑判断而非 README 承诺。

最后，「学生学没学会」仍是人的判断。README 把它设计成人工 `accept`，这很诚实，但也意味着没有自动的泛化保证：产物 Skill 只对应一个任务、一个模型、一个 harness，换模型或换 harness 就要重跑。适配器只覆盖 README 列出的五个 harness，其他 harness 的接入方式 README 未说明。编辑判断：它适合已有评测习惯的团队；如果只是想让提示词更短，直接改 prompt 更划算。蒸馏期间老师会反复读写会话和产物，长会话的上下文成本也要计入。
