# 掘金技术写作

写出来的东西要像一个真跑过的人在讲，不像一个模型在总结。三件事按顺序做：定模式 → 填结构 → 过自检。

样本取自本站作者在掘金关注的 104 位前端作者中产出最稳定的 7 位，实测数据见文末。

## 一、先定模式

四种模式，一篇只用一个，不要混。

| 模式 | 什么时候用 | 代表 | 实测 |
|---|---|---|---|
| **A 认知纠错** | 题目被写烂了，但读者有共同盲区 | ErpanOmer | 6600 字 / 15 代码块 / 8 图 / 段均 29 字 |
| **B 体系化长文** | 一个主题能被拆成完整分类树 | 大漠、尤水就下 | 12000–13500 字 / 20+ 代码块 / 段均 34–43 字 |
| **C 问题驱动** | 排障、源码答疑、需求变更 | 熊的猫、kyriewen | 5700–5900 字 / 5–8 代码块 / 段均 26–33 字 |
| **D 清单测评** | 技巧合集、新工具、新框架 | JowayYoung、涛涛ing | 4000–7300 字 / 加粗 38–82 处 |

本站笔记的默认选择：**源码与架构用 C，一个主题能吃透就用 B，被写烂的经典题用 A，工具与技巧合集用 D**。

### A 认知纠错（ErpanOmer）

```
标题：问句或断言，直接挑战共识（"为什么很多人觉得前端很简单？"）
开头：承认读者看过很多 → 指出共同盲区 → 承诺一个具体收获
正文：H3 拆成可执行步骤（第一步…第九步），每步配代码或图
结尾：回到真实工作场景（"这些知识在真实工作中怎么用？"）
```

标题几乎全是问句。开头第一句就否定一个默认认知，不给背景铺垫。

### B 体系化长文（大漠 / 尤水就下）

```
标题：主题 + 指南/揭秘，或一个具体现象
开头：描述一个熟悉的现象（"如果你拆开一个稍微复杂的 Web 应用…"）
正文：H2 是概念层（本质 / 尺寸关系模型），H3 是分类（绝对关系 / 全局关系 / 局部关系…）
结尾：不总结，最后一节就是最后一个分类
```

大漠那篇 13500 字、22 个代码块，全靠分类树撑起来：先把「单位」重新定义成「跟随谁变化」，再按「跟随对象」分成 6 类，每类一节。**长文的长度来自分类的完备性，不是来自废话。**

尤水就下则用短名词做 H2（Block 是啥 / 数据拍平 / 分块加载 / 虚拟滚动），一节解决一个子系统。

### C 问题驱动（熊的猫 / kyriewen）

```
标题：一个具体的人问了一个具体的问题（"校招生问我在 vue 中，什么时候该用 render 函数？"）
开头：真实工作场景，一句话交代谁在什么情况下遇到什么
正文：H2 是问句或判断句，每节回答一个子问题
结尾：熊的猫写「总结」，kyriewen 列参考资料，都不喊口号
```

熊的猫的开头永远是「前言」+ 一个同事/校招生/产品的具体场景，段均只有 26 字——最短，最好读。

kyriewen 的 H2 是编号 1..6，每个标题本身就是一句结论（"全选框亮不亮，不能看有没有选中项"）。

### D 清单测评（JowayYoung / 涛涛ing）

```
标题：数字 + 收益 + 来源背书（"8则未必知道且超级实用的纯CSS布局排版技巧 | 网易四年实践"）
开头：一句判断，不是行业背景
正文：一、二、三…每节一个技巧/一个功能，配截图或代码
结尾：链接 + 一个真问题
```

注意区分：JowayYoung 的「TRAE 活动分享」是 PPT 整理（28 图 / 82 处加粗），那是会议纪要的写法，不要当模板；他的「8则CSS技巧」才是清单体的标准。

## 二、硬规则

七份样本的共同点，违反任何一条都会立刻露出"生成"的味道。

1. **标题 ≤ 22 字**，必须含一个具体名词或数字。禁用「浅谈 / 漫谈 / 一文读懂 / 深入浅出」。
2. **第一句不能是背景**。七篇里没有一篇以「随着…的发展」「在当今…」开头。第一句要么是判断，要么是场景，要么是问句。
3. **小标题是句子或具体名词，不是抽象概念**。写「全选框亮不亮，不能看有没有选中项」，不写「全选框状态管理」。
4. **每段 1–3 句**。样本平均 26–43 字一段，超过 4 句就拆。熊的猫 26 字最值得学。
5. **每个抽象结论，200 字内必须跟一个可验证的东西**：代码、命令、输出、数字、截图。
6. **代码块前一句说这段在干什么，后一句说输出是什么**。不贴裸代码。
7. **加粗只给结论句**。样本从 16 到 82 处不等，但每一处都是判断句，不是随便强调。
8. **不用「首先 / 其次 / 最后」串全文**。用编号、步骤，或直接分段。
9. **结尾不写「希望对你有帮助」**。给一个动作、一份资料，或一个没解决的问题。

## 三、句子层

- 用「你」指读者，用「我」指自己。样本里两种人称都很密。
- 短句优先。一句话说不完就断成两句，不要靠逗号串。
- 具体数字胜过形容词：「快 12 倍」而不是「快很多」；「3 个 G」而不是「大量」。
- 允许口语（「我差点儿没瞎」「先别急着抄」），但不允许网络烂梗堆叠。
- 不确定的地方直接写「这点我还没搞懂」。本站笔记的 `kind` 里本来就有「重建」，半成品是允许的。

## 四、自检清单

写完逐条过，有一条不过就改：

- [ ] 遮住标题，只读第一段，还知道这篇在讲什么吗？
- [ ] 每个 H2 单独拿出来，是不是一句能立住的话？
- [ ] 每个抽象结论后面，有没有一个能点开核对的东西？
- [ ] 删掉所有形容词，还剩多少信息？
- [ ] 有没有哪一段超过 4 句？
- [ ] 加粗的是判断句，还是随便强调的词？
- [ ] 结尾是不是「希望对你有帮助」这类废话？
- [ ] 通篇有没有出现「首先/其次/综上所述/值得注意的是」？

## 五、反例

这些句子一出现，整篇的可信度就没了：

- 「在当今快速发展的互联网时代…」
- 「本文将深入浅出地介绍…」
- 「总的来说，X 是一把双刃剑」
- 「不仅…而且…更重要的是…」（三段式排比）
- 「让我们一起探索…」
- 用三个并列短句凑节奏：「更快、更稳、更强。」

## 六、写本站笔记时的落地

笔记是 MDX，frontmatter 四个字段全必填，缺一个构建就失败：

```yaml
---
title: 为什么这个站用 MDX 而不是 CMS
summary: 一句话说清这篇解决什么问题
kind: tool        # source | architecture | rebuild | tool
publishedAt: 2026-11-22
---
```

`kind` 决定列表页的分组，选错会让左栏出现空锚点。正文里能用的自定义组件只有 `CodeBlock`（代码围栏自动转，不用手写）和 `Figure`（配图用），其余走原生标签，不要自己造组件。

要配图的话另走 `juejin-illustration`：先判断该不该配，再决定内联 SVG 还是截图。**技术示意图不许用 AI 生图。**
